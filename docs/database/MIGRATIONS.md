# Database Migrations

## Overview
We use Supabase migrations to manage schema changes. All changes to the database structure (tables, columns, policies, functions) must be committed as migration files.

## Workflow

### 1. Create a Migration
To create a new migration, use the Supabase CLI (if installed) or manually create a file in `supabase/migrations/`:

```bash
# Timestamp_name.sql naming convention
20240210120000_add_search_logs.sql
```

### 2. Write SQL
Write pure SQL in the file.
```sql
create table public.search_logs (
  id bigint generated by default as identity primary key,
  search_term text,
  created_at timestamptz default now()
);

alter table public.search_logs enable row level security;
```

### 3. Apply Migration
If using local development:
```bash
supabase db reset   # Wipes local DB and reapplies all migrations
# OR
supabase migration up # Applies pending migrations
```

For production, migrations are usually applied via the Supabase Dashboard (SQL Editor) or a CI/CD pipeline (e.g., GitHub Actions using `supabase db push`).

> [!WARNING]
> Always test migrations locally or on a staging project before running them in production.
